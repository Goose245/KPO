# Домашнее задание №2. Модуль «ПОС»

Консольное приложение для системы «Преподавательская Оценка Студентов» (ПОС), спроектированное на языке Go с применением принципов **Domain-Driven Design (DDD)**, **Clean Architecture** и паттернов **GoF**.

## 1. Запуск и требования
* **Рабочая директория:** Запуск должен производиться из корневой папки проекта (`pos_system/`). Папка хранилища `data/` создается автоматически при старте.
* **Запуск программы:** `go run ./cmd/pos` (запускает интерактивное консольное меню).
* **Запуск тестов:** `go test ./... -v` (запускает юнит-тесты домена и фасада).
* **Ожидаемый результат:** Приложение предоставляет интерактивный интерфейс. Ограничение реализации: база данных заменена на локальные JSON-файлы, загружаемые в память при операциях. В конце работы можно экспортировать актуальную ведомость в `data/summary_export.json`.

## 2. Архитектура (Clean Architecture / Ports & Adapters)

Проект разделен на слои с направлением зависимостей строго внутрь (к домену):

* **`internal/domain` (Ядро)**: Не зависит ни от чего. Содержит бизнес-правила, сущности с защищенным (приватным) состоянием, объекты-значения, доменный сервис и порты (интерфейсы `Repository`).
* **`internal/application` (Сценарии/Use Cases)**: Зависит только от домена. Содержит паттерн Фасад (`POSFacade`), координирующий логику, и **строгий слой DTO с мапперами**, благодаря которому доменные модели не «утекают» во внешний мир.
* **`internal/infrastructure` (Адаптеры)**: Реализация портов домена. **JSON-хранилище** — потокобезопасные репозитории (`sync.RWMutex`), строго обрабатывающие ошибки файловой системы.
* **`cmd/pos/main.go` (Точка входа / DI-контейнер)**: Внешний слой (Composition Root). Здесь собирается граф зависимостей и запускается консольный UI.

## 3. Карта DDD и Бизнес-правила

* **Ubiquitous Language (Единый язык):** Студент (`Student`), Критерий (`Criterion`), Оценка (`Evaluation`), Рубрикатор, Итог (`Summary`), Транспортные объекты (`DTO`).
* **Entity (Сущности) и Value Object:**
  * `Student` — идентифицируется по `ID`.
  * `Criterion` — содержит настройки оценивания (`MaxScore`, `Weight`).
  * `Evaluation` — факт выставления оценки. Поля сущности инкапсулированы (приватны). 
  * `Score` — Value Object (`type Score float64`), явно отделяющий баллы от обычных чисел.
* **Invariants (Инварианты):**
  * Защита от `NaN` и `Infinity` при выставлении баллов и весов.
  * Оценка не может быть `< 0` или `> MaxScore`.
  * Нельзя уменьшить `MaxScore` критерия, если уже существуют оценки, превышающие новый порог.
  * Оценка выставляется только по существующему критерию студенту, который есть в базе.
* **Domain Service (Доменный сервис):**
  * `SummaryService` — оркестрирует расчет итогового балла на основе переданной стратегии.

### Политика оценивания и расчета итога
* **Формула итога:** `(Score / MaxScore) * Weight`. Шкала не ограничена 1.0 и зависит от суммы заданных пользователем весов. 
* **Пропуски:** Если у студента нет оценки по существующему критерию, её вклад в итог равен `0`.
* **Повторное выставление:** При повторном выставлении оценки тому же студенту по тому же критерию **старая оценка перезаписывается** (дубликаты не суммируются).
* **Отмена оценок:** Ошибочную оценку можно полностью удалить через соответствующий пункт меню.

## 4. Обоснование паттернов GoF

В проекте применено 3 паттерна (по одному из каждой группы) для решения конкретных болей:

### 1. Порождающий: Фабрика (Simple Factory)
* **Где:** `NewEvaluation(studentID, criterion, score)` в домене.
* **Какую боль закрывает:** Гарантирует единую точку создания оценки. Фабрика надежно инкапсулирует внутреннее состояние (поля приватные) и не позволяет собрать невалидный объект, отклоняя выходы за границы критерия и нечисловые значения (NaN/Inf).

### 2. Структурный: Фасад (Facade)
* **Где:** `POSFacade` в слое `application`.
* **Какую боль закрывает:** Скрывает от консольного клиента (`main.go`) координацию репозиториев. UI не занимается проверками существования ID, контролем конфликтов критериев и конвертацией DTO. 

### 3. Поведенческий: Стратегия (Strategy)
* **Где:** Интерфейс `CalculationStrategy` и реализация `WeightedAverageStrategy`.
* **Какую боль закрывает:** Позволяет динамически подменять формулу расчета итога (доказано в `evaluation_test.go` подменой на `MockStrategy`), не изменяя код сервиса (принцип Open/Closed).

## 5. Тестирование

В проекте реализован минимальный необходимый набор тестов, покрывающий правила из ТЗ:
* Проверка формулы итога.
* Проверка перезаписи при исправлении оценки.
* Проверка неизвестных студентов/критериев.
* Проверка недопустимых числовых значений NaN/Inf и границ MaxScore.
* Подмена стратегии расчета).
